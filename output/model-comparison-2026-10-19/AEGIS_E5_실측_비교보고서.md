# AEGIS v2 · korean-pii-e5-base 프로젝트 적합성 실측 비교

시험일: 2026-10-19. 현재 A 모델을 대조군으로 포함한 별도 CPU 시험. 제품 코드·모델 설정·설치 패키지는 변경하지 않았다.

**판단: E5는 기존 커뮤니티 예시의 이름 오탐을 줄였고 짧은 글의 속도도 실용적이었다. 하지만 새 진단 사례 전체에서 현재 A보다 정확한 이름·주소 구간을 더 많이 찾지는 못했다. AEGIS는 가볍고 오경보가 적었으나 실제 이름 미탐이 늘었다. 이번 결과로 이름·주소 담당 모델을 즉시 전면 교체하는 것은 권하지 않는다.**

## 실행 조건과 범위

- PC: Intel(R) Core(TM) Ultra 5 325, RAM 31.37 GiB(32GB급), Windows, GPU/NPU 미사용.
- 각 모델을 별도 프로세스에서 순서대로 실행했다. 기본 CPU 4스레드, 배치 1. 모델을 로딩한 뒤 시간은 3회 반복 중앙값이다. UI·통신·규칙 탐지 시간은 제외했다.
- AEGIS는 공개 ONNX INT8/ONNX Runtime 1.23.2, E5와 A는 PyTorch 2.9.1+cpu FP32/Transformers 4.57.6이다. 실제 사용할 수 있는 배포 형태의 비교이며 양자화 방식까지 같게 맞춘 아키텍처 비교는 아니다.
- 입력 한도는 A·AEGIS 512토큰, E5 256토큰이며 64토큰을 겹친다. 긴 글을 버리지 않고 끝까지 검사한다. 문맥 길이 차이도 결과에 영향을 준다.
- 새 합성 사례 75개(개인정보 없는 문장 30개 포함), 정답 62구간(이름 46·주소 16)을 결과 확인 전에 고정했다. 이전 진단 사례 116개는 별도 회귀 비교에 사용했다. 현재 저장 예시 3개의 제목·본문은 추가 관찰로 분리했다.
- 일반어·짧은 이름·조사 경계·상세 주소를 집중적으로 시험했다. 임의 표본이며 실제 사용자 전체의 정확도나 오탐률 추정이 아니다. 외부 학습 자료와 중복이 없다는 검증도 아니다.
- 앱에서 모델이 담당하는 이름·주소만 평가했다. 전화·주민번호 등 기존 규칙의 성능이나 전체 앱 통합 점수가 아니다. 모든 추론에서 네트워크 연결 함수를 차단했고 시도 0회를 확인했다.

AEGIS 결과 병합은 모델을 다시 돌리는 작업이 아니다. 이 시험에서는 바로 붙은 성·이름 한 쌍, 공백·쉼표로 인접한 서로 다른 주소 요소만 합쳤다. 추가 학습이나 점수 조정은 하지 않았다. 제작자의 모든 검증 규칙을 재현한 것은 아니다. E5는 원출력과 모델 카드에 제시된 조사 제거 후 출력을 모두 보존했다.

이 시험의 단순 결과 정리에 든 시간은 새 사례 한 입력당 AEGIS 약 0.0014ms, E5 약 0.0034ms였다. 계산량보다 서로 다른 이름을 잘못 합치거나 이름 끝을 잘라내지 않는 정확성이 더 중요한 문제다.

오경보는 AEGIS가 적었지만 실제 이름도 더 놓쳤다. E5는 완전히 놓친 이름이 적었지만 정확한 이름·주소 경계까지 포함하면 현재 A의 우위가 남았다. E5의 제공 보정 코드는 이번 자료에서 성능을 낮췄다. 예를 들어 원출력의 ‘이송아’를 ‘이송’으로 줄였다. 조사처럼 보이는 글자가 실제 이름의 일부일 수 있으므로 그대로 도입하면 안 된다.

| 박하차를 준비했습니다. | 성명 없음 | 박하차를 포함한 구간을 성명으로 오인 |

이전 116개 회귀 사례의 이름·주소 49구간에서는 A 완전 45개, AEGIS 병합 후 34개, E5 제공 보정 후 32개였다. 이전 자료는 A를 선정하는 데 이미 사용했으므로 독립 검증으로 해석하지 않는다. 세부 원출력·오류 분류는 scores.json 및 results-*.json에 보존했다.

## 실제로 제공했던 저장 예시

789자 커뮤니티 본문에서 E5는 실제 이름 4곳을 모두 표시하고 ‘우노·젠가·박하차’를 성명으로 표시하지 않았다. 현재 A는 실제 이름 4곳 외에 ‘우노와 젠가’, ‘박하’를 성명으로 표시했다. AEGIS는 일반어 오탐은 없었지만 반복된 이름 2곳을 놓쳤다. AEGIS에 문장 단위 입력을 적용하면 이 예시에서는 이름 4곳을 모두 찾았다.

E5는 이 예시와 행사 공지의 주소에서 도로명·번지까지 찾고 건물·층·호수 부분을 누락하는 경우가 있었다. 행사장 공개 주소를 위험으로 표시할지는 별도의 제품 정책 문제이며, 이 예시들의 주소를 새 75개 개인정보 정확도 점수에 섞지 않았다. 새 주소 진단 사례는 개인 집·배송지로 문맥을 명시했다.

2스레드 시험은 병렬 계산 여유가 줄었을 때의 관찰이다. 구형 CPU나 RAM 8GB PC를 실제로 시험한 결과는 아니다.

## 첫 준비 시간과 메모리

| 관측 항목 | 현재 A | AEGIS | E5 |
| --- | ---: | ---: | ---: |
| 저장 예시 시험의 새 프로세스 → 첫 결과 | 10.17초 | 3.29초 | 10.57초 |
| 주 시험 중 최대 실제 상주 메모리 | 0.41GB | 0.39GB | 2.22GB |
| 주 시험 종료 시 실제 상주 메모리 | 0.37GB | 0.38GB | 1.71GB |
| 주 시험 종료 시 private commit | 0.70GB | 0.60GB | 2.12GB |

이는 모델 프로세스의 메모리이며 화면·서버·OS·브라우저 사용량은 별도다. E5의 BF16 파일은 CPU 호환성을 위해 FP32로 로딩해 파일 용량보다 실행 메모리가 크게 늘었다. 최대 메모리에는 로딩 중 일시적 증가도 포함된다. private commit은 실제 상주 RAM과 다르다.

처음 실행한 주 시험의 준비 시간은 A 10.83초, AEGIS 25.37초, E5 14.32초였다. 당시 파일 확인 작업과 초기 캐시 상태가 영향을 줄 수 있어, 이를 보장값이나 순수 모델 추론 시간으로 쓰지 않았다. 이후 별도 검증/예시 실행에서는 AEGIS 3.29~3.31초, E5 10.57~11.03초였다. OS 캐시를 지우거나 재부팅한 시험은 아니다. 앱 통합 후 첫 검사 시간은 별도로 측정해야 한다.

## 일반 사용자 관점의 판단

- GPU는 필수가 아니다. 두 모델 모두 이번 PC에서 CPU만으로 검사했다. 모델 파일을 준비한 이후에는 인터넷 없이 검사할 수 있다.
- AEGIS는 약 0.4GB의 모델 프로세스 최대 상주 메모리와 짧은 준비 시간 때문에 보급형 PC용 후보로 유리하다. 다만 이름 미탐을 수용할 수 있는지 확인해야 한다.
- E5도 수백~수천 자 글을 버튼으로 검사하는 용도는 사용 가능성이 높다. 16GB급 PC를 우선 검증 대상으로 삼을 만하지만, 이것은 최소 사양 인증이 아니다. 8GB PC는 브라우저 등 다른 프로그램과 함께 사용할 때 약 2.2GB의 모델 최대 사용량이 부담이 될 수 있다. 해당 메모리 용량 PC에서 직접 확인하지 않았다.
- E5의 3만 자 약 16.9초는 현재 앱의 모델 검사 제한 20초에 여유가 적다. 더 느린 PC에서는 시간 초과 가능성이 있어 적용 시 긴 글 처리·진행 표시·취소·제한 시간을 재검토해야 한다.
- 현재 앱처럼 한 번 준비한 프로세스를 재사용해야 한다. 검사할 때마다 모델을 다시 불러오면 짧은 글에서도 준비 시간이 대부분을 차지한다.
- E5 양자화나 다른 CPU 실행 형식으로 부담을 낮출 가능성은 있지만 이번 시험에서는 수행하지 않았다. 속도·메모리·정확도 개선을 미리 보장하지 않는다.

## 문장 단위 검사의 효과

새 자료 중 17개 선택 입력(정답 20구간)에서 기존 길이별 분할·문장 하나씩·앞뒤 문장 포함을 비교했다. 분리는 마침표/물음표/느낌표와 줄바꿈을 이용한 단순 방식이며 전문 한국어 문장 분리기를 평가한 것은 아니다. 긴 문장은 다시 토큰 구간으로 나눈다.

| 모델 | 기존 방식 완전 탐지 / 추가 표시 | 한 문장씩 | 앞뒤 문장 포함 |
| --- | ---: | ---: | ---: |
| A | 16 / 10 | 15 / 13 | 16 / 11 |
| AEGIS | 13 / 1 | 12 / 1 | 13 / 1 |
| E5 | 16 / 2 | 16 / 6 | 16 / 5 |

이 표는 각 모델의 시험용 보정 후 출력 기준이다. 문장 단위가 항상 낫지는 않았다. 기존 커뮤니티 글에서는 AEGIS가 개선됐지만, E5는 행사 글을 문장별로 나누자 ‘이동식 안내판’의 ‘이동식’을 성명으로 표시하기도 했다. E5의 커뮤니티 검사 시간도 기존 약 0.31초에서 문장별 약 0.48초, 앞뒤 문장 포함 약 1.01초로 늘었다(문장 방식은 각 1회 관찰).

## 적용 결정

현재 전체 이름·주소 담당 모델은 유지하는 것이 타당하다. 새 후보 둘 중에서는 일반 PC 부담과 오경보 억제에 AEGIS, 실제 이름을 놓치지 않는 방향과 기존 커뮤니티 이름 탐지에 E5의 장점이 있다. E5가 더 크고 연결이 단순하다는 사실만으로 우수성을 판단할 수 없다. 이 프로젝트에서는 이름 경계와 상세 주소를 끝까지 표시하는 능력까지 필요하다.

E5를 계속 검토한다면 이름 결과와 주소 결과를 분리해 품질을 판단하고, 제공 조사 제거 코드를 먼저 보완해야 한다. 다만 실제 두 모델을 동시에 탑재하는 설계는 메모리·속도 비용이 추가되므로 이번 결과만으로 권하지 않는다. AEGIS는 짧은 이름과 반복 등장 이름의 미탐이 해결되는지 우선 확인해야 한다. 어느 쪽이든 이번 사례에 맞춰 규칙을 고친 뒤 같은 자료만 다시 시험하면 과적합될 수 있으므로 다음 확인에는 별도 자료가 필요하다.

## 재현·검증 기록

- AEGIS: `YATAV-ENT/aegis-personal-pii-ner@3a1d4f61e156035a22d820b59c78e4d5e5cc6f6f`. 다운로드 파일 크기·SHA-256은 model-manifest.json에 기록. 큰 가중치의 배포 LFS 해시도 대조했다.

- E5: `FrameByFrame/korean-pii-e5-base@a308c54b4407819624a5661e31e162a269f39818`. 다운로드 파일 크기·SHA-256은 model-manifest.json에 기록. 큰 가중치의 배포 LFS 해시도 대조했다.

- A: 현재 앱의 고정 모델 파일을 읽기만 했다. 새 모델 파일은 tmp/model-comparison-2026-10-19/models에 있다. 이전 시험용 Python 환경을 재사용했으며 패키지 설치·업데이트는 하지 않았다.

- AEGIS와 E5 각각 새 사례 75개에서 별도 순차 디코더와 구간 결과를 대조했고 모두 일치했다. AutoTokenizer의 토큰 ID·원문 위치를 배포 tokenizer.json 직접 실행과 대조했고 모두 일치했다. 모델이 출력한 한국어·이모지 구간의 UTF-16 변환도 확인했다.

- Transformers의 Mistral 관련 경고가 두 모델에서 출력됐다. 설치 코드의 특정 버전 분기에서 비-Mistral 구분 없이 경고하는 것을 확인했다. 모델은 BERT/XLM-R이며 토크나이저를 임의 수정하지 않았다. 배포 파일 직접 실행과의 일치 검증 결과는 validation-*.json에 있다.

- 제품 소스·설정·빌드 50개 파일의 작업 중 스냅샷과 종료 시 해시가 일치했다. 설치 런타임 전체 해시 검사는 오래 걸려 중단했고 이 대조 범위에서 제외했다. 제품 편집은 수행하지 않았다.

- 실행 스크립트는 research/model-comparison-2026-10-19, 원문 정답은 cases-frozen.json, 전체 예측은 results-*.json, 제공 예시 관찰은 sample-posts-*.json, 집계는 scores.json에 있다. 기존 자료·결과는 덮어쓰지 않았다.
