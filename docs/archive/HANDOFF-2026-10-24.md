## 2 처음부터 이어진 대화와 결정의 흐름

### 2.1 원계획서 제공과 ko-pii 조사

사용자는 `게시전_개인정보_노출_자가진단_도구_프로젝트계획서_v2.docx`를 제공하고 구현 전에 정할 사항과 ko-pii 활용 방법을 자세히 조사해 달라고 요청했다. 원계획서는 전시회 출품을 염두에 둔 개인 프로젝트로, Windows 데스크톱, Python과 FastAPI, 웹 화면, ko-pii, pywebview, OCR과 EXE 배포를 포함했다.

원계획서의 장기 흐름은 본문과 첨부 입력, 탐지, 개별·결합 위험도, 사용자 선택, 마스킹이었다. 그러나 이후 사용자가 초기 범위를 탐지와 검토 중심으로 좁혔다. 원계획서에 있는 기능을 모두 현재 버전에 구현해야 하는 것으로 해석하지 않는다. 원본은 수정하지 않았다.

ko-pii 배포판과 실제 API를 조사하고 가상 입력, 문자 위치, 선택 마스킹, 최소 DOCX 추출 등을 별도 실험했다. 활용 안내 PDF를 만들었다. 라이브러리 기능을 실험한 것과 제품에 연결한 것은 다르다. 파일 추출이나 마스킹 실험이 존재해도 현재 앱은 제목·본문 텍스트만 검사한다.

### 2.2 위험도와 마커의 목적 정리

사용자는 위험도 기준을 더 구체화해 달라고 요청했고, 개인정보가 무엇인지 알리고 해당 위치를 위험도별 색으로 구별하자는 방향을 제시했다. 수정하기 전에 검토가 제대로 되는지 확인하는 것을 우선한다고 명시했다.

초기 마커 디자인에 만족하지 않아 다른 표시 방식을 비교했다. 배경 전체를 강하게 칠하는 표현보다 읽기 편한 표시를 검토했고, 비교 시안에서 ‘선택 강조’를 살펴본 기록이 있다. 최종적으로 구체화된 요구는 개인정보 후보 글자 자체에 위험도 색을 적용하고, 오른쪽 목록에도 같은 색을 사용하는 것이다. 비교 시안의 선택 상태를 최종 제품 기능 승인으로 간주하지 않는다.

### 2.3 작성 화면과 대시보드부터 디자인

사용자는 깔끔한 스타일, 게시글 작성 영역, 대시보드, 후보가 많을 때의 리스트를 먼저 설계하자고 요청했다. 이후 두 화면을 명확히 했다. 첫 화면에서 제목과 본문을 쓰거나 가져오고, 검사 후 두 번째 화면에서 입력한 전체 글과 개인정보 후보를 함께 확인한다.

결과 화면은 발췌 문단만 보여주지 않고 원문 전체를 유지한다. 위험도 색은 서로 쉽게 구분돼야 하며, 대시보드는 위험도별 건수와 후보 목록을 제공한다. 사용자가 결과를 확인한 뒤 어떤 도움을 받을지, 예를 들어 확인 완료·오탐 판정·마스킹은 디자인 검토 후 별도로 정하기로 했다.

### 2.4 웹과 개인 프로그램의 비교

사용자는 공유 웹사이트보다 개인이 사용하고 데이터를 관리하는 프로그램이 적절한지 질문했다. HTML/CSS/JavaScript 화면을 로컬 서버나 데스크톱 창에서 사용할 수 있는 방향을 비교했다. 화면 기술이 웹 기술이라는 사실과 데이터가 외부 서버로 전송된다는 사실은 별개로 정리했다.

Windows와 macOS의 실행·파일 선택·패키징 차이를 검토했고, 로컬 웹앱에서 PC와 스마트폰 지원이 어떻게 다른지 논의했다. ‘스마트폰 브라우저에서 PC에 접속’은 보류 아이디어로 남겼다. 사용자가 실제로 확인하려던 것은 PC와 스마트폰 각각에서 사용할 수 있는지였으며, 이후 우선 PC에 집중하기로 결정했다.

### 2.5 기술과 첫 플랫폼 확정

사용자는 화면 기술로 React + TypeScript + Vite, 첫 플랫폼으로 Windows를 명시적으로 선택했다. Python + FastAPI + ko-pii는 기존 권장 구성을 바탕으로 실제 구현에 적용했다. 현재 기본 실행은 pywebview와 WebView2의 전용 창이며 개발용 브라우저 실행도 남겨 두었다. 전용 창은 현재의 구현 선택이지, 이전에 남겨 둔 모든 배포 선택이 확정됐다는 뜻은 아니다.

같은 인터넷을 사용하는 사람이 데이터를 볼 수 있는지도 확인했다. 로컬 서버를 127.0.0.1에만 묶고 외부 전송과 API 접근을 제한하는 기준을 마련했다. 오탐·미탐 가능성과 게시 전 직접 재검토 권고를 명시하기로 했고, 제안한 시험 항목을 검증 기준으로 채택했다.

### 2.6 저장과 작업 재개 흐름 확정

사용자는 직접 저장·불러오기 기능을 요청했고, 다음 흐름을 결정했다.

**글 작성 → 저장 → 컴퓨터 종료 → 프로그램 실행 → 불러오기 → 이어서 작성**

이는 저장한 작업을 다시 시작하는 흐름이다. 검사를 위해 반드시 저장하거나 컴퓨터를 종료해야 한다는 의미가 아니다. 자동 저장과 갑작스러운 전원 종료 후 미저장 글 복구는 포함하지 않았다.

행사 운영자와 일반 커뮤니티 사용자를 대상으로 삼자는 방향도 제안했다. 이를 대표 사용 시나리오로 삼되, 대상 사용자 확정을 별도로 완료했다는 기록은 없다. 행사 모집·안내·결과 공지, 모임 모집·나눔·거래·후기 등을 평가 후보로 정리했다. 유형별 실제 이용량 통계는 확보하지 못했으므로 특정 유형이 가장 많이 쓰일 것이라고 단정하지 않았다.

### 2.7 저장 위치 제안이 변경된 과정

처음에는 문서 폴더 아래 영어 프로젝트명 폴더를 자동 생성하고 기본 저장 위치를 변경할 수 있게 하자는 제안이 있었다. 이후 문서 폴더가 OneDrive와 동기화될 수 있다는 우려로, 사용자가 원하는 위치에 작업 파일을 저장하고 직접 그 파일을 선택해 불러오는 방식으로 변경했다.

최신 결정은 고정 작업 폴더를 강제하지 않고 사용자가 위치를 선택하도록 하는 것이다. 제목을 기본 파일명으로 추천하며, Windows 파일명에 사용할 수 없는 특수문자는 제외한다. 원래 글 제목은 파일 안에 그대로 보존한다. 파일명을 사용자가 바꿀 수 있고, 제목을 수정했다고 이미 저장된 파일 이름을 자동으로 바꾸지 않는다.

OneDrive 감지·경고·차단은 1차 구현을 사용한 뒤 결정하기로 했다. 저장 위치를 선택한다는 이유로 동기화가 자동 차단되는 것은 아니다. 저장 취소·실패, 빈 제목, 예약 이름, 같은 이름, 외부 수정, 손상 파일, 미저장 변경 등 예외 상황을 구현 기준에 포함했다.

### 2.8 저장 UI 시안과 종합보고서

시작 화면에 새 글 작성·저장한 글 불러오기를 추가하고, 작성·결과 화면에 공통 파일 도구 모음을 배치했다. 추천 파일명, 위치 선택, 미저장 안내 등 인터랙티브 HTML 시안을 만들었다. 이 시안의 저장·불러오기는 가상 동작으로 실제 파일 저장 기능이 아니었다.

사용자 요청으로 논의를 종합한 보고서를 PDF와 DOCX로 작성했다. 이 보고서는 구현 전 설계 기록이므로 현재 기능 완료 여부는 소스와 검증 기록을 우선한다.

### 2.9 1차 구현과 실행 확인

사용자는 이미지에 표시된 GPT-6 Astra · Extra High 설정으로 1차 구현을 요청했고, 현재 채팅에도 그 설정이 선택됐다고 직접 확인했다. 모델 설정 확인은 이미 끝난 논의이므로 인수자가 같은 확인을 다시 요청할 필요는 없다. 이 기록이 다음 채팅의 실제 모델 설정을 보장하는 것은 아니다.

React 화면, 로컬 API, 실제 ko-pii 검사, Windows 창, 저장·불러오기, 위치 표시와 오류 처리를 구현했다. Python 자동 시험 22개, 화면 통합 12개 흐름, Windows 창과 VBS 실행 경로를 확인했다. 콘솔 없는 실행에서 서버 로그 설정이 실패하는 문제와 실행 도우미의 숨김 설정으로 실제 창이 안 보이는 문제를 수정했다.

### 2.10 커뮤니티 게시글 3종 시험과 문서화

사용자는 오탐이나 미탐이 생길 수 있는 커뮤니티 글을 약 3개 만들어 점검하고 문서화해 달라고 요청했다. 독서 모임 모집, 중고거래와 나눔, 개인정보를 넣지 않은 취미 후기의 합성 글을 만들고 기대 항목을 먼저 고정했다. 실제 앱의 검사 API와 화면을 사용했다.

기대 항목 16개 중 완전 탐지 9개, 부분 탐지 2개, 유형 오분류 1개, 미탐 4개를 확인했다. 추가 오탐은 10개였다. 원문·정답·실제 결과·재현용 작업 파일과 8쪽 PDF를 제공했다. 이 단계에서 제품 탐지 규칙을 수정하지 않았다.

### 2.11 관련 논문 조사와 현재 대화의 도착점

사용자는 오류를 줄이는 방법을 관련 논문을 참고해 찾아 달라고 요청했다. 한국어 비식별화와 개체명 인식, GLiNER, CheckList, TAB 등 핵심 논문 6편을 조사했다. 현재 오류를 문장 쌍으로 추가 비교하고, 규칙 보완과 문맥 판단 및 한국어 모델을 단계적으로 결합하자는 개선안을 문서화했다. 개선 코드는 적용하지 않았다.

가장 최근 사용자는 ‘ko-pii 학습 모델 연결이 나만의 모델을 만드는 것인지’ 질문했다. 답변은 이미 학습된 모델 연결, 기존 모델 추가 학습, 처음부터 학습을 구분했다. 연결 기능은 학습된 탐지기를 사용할 수 있게 하는 장치이며, 연결 자체가 자동 학습은 아니다. 기존 모델을 비교한 뒤 필요하면 커뮤니티 자료로 추가 학습하는 방안을 권했다. 사용자가 모델 선정·다운로드·학습·통합 실행을 별도로 확정한 상태는 아니다.

## 4 화면과 사용 흐름

### 4.1 시작과 작성

시작 화면은 새 글 작성, 저장한 글 불러오기, 가상 예시 글로 살펴보기를 제공한다. 작성 화면은 제목과 본문 입력, 글자 수, 파일 도구 모음, 검사 버튼과 재검토 안내를 제공한다. 제목이나 본문에 유효한 글이 있으면 검사할 수 있다. 저장은 검사의 필수 선행 단계가 아니다.

공통 파일 도구 모음에는 새 글, 불러오기, 저장, 다른 이름으로 저장과 파일 상태가 있다. 전용 창에는 프로그램 종료 항목도 있다. 저장하지 않은 변경사항과 마지막 저장 시각을 구별한다.

### 4.2 검사 결과와 많은 후보 처리

결과 화면 왼쪽에는 제목·본문 전체를 원문 그대로 표시한다. 후보만 글자색을 바꾸고, 오른쪽에는 총 발생 위치 수, 위험도별 건수, 색상 막대, 위험도 필터, 후보 목록을 제공한다. 같은 값도 등장 위치마다 별도 후보로 센다.

후보 목록은 위험도별로 묶는다. 한 그룹에서 처음 30개를 보여주고 ‘더 보기’로 30개씩 추가한다. 후보를 누르면 원문 위치로 이동하고 포커스를 준다. 제목과 본문에서 발견된 항목을 구분한다. 목록 번호가 원문 순서를 따르더라도 그룹 배치는 위험도순이므로 목록의 화면 순서를 원문 순서라고 가정하지 않는다.

현재 색상은 심각 `#b4233b` 빨강, 높음 `#7442c8` 보라, 보통 `#205fbd` 파랑, 낮음 `#08766d` 청록, 참고 `#866000` 갈색이다. 색과 위험도 명칭을 함께 사용한다. 최종 색상 승인이나 다양한 색각·보조기기 조건 검증이 완료된 것은 아니다.

### 4.3 상태와 안내

안내 문구는 다음과 같다.

> 자동 검사는 개인정보를 잘못 표시하거나 놓칠 수 있습니다. 게시 전, 표시되지 않은 부분까지 직접 한 번 더 확인해 주세요.

작성 화면의 검사 버튼 근처와 결과 화면 상단에 표시하며, 후보가 0건이어도 유지한다. ‘탐지된 후보가 없습니다’는 안전함이나 개인정보 부재의 보증이 아니다. 검사 실패·시간 초과를 0건 성공으로 표시하지 않는다.

원문을 수정하면 기존 결과를 무효화한다. 검사를 누른 뒤 원문이 바뀌면 뒤늦게 도착한 이전 응답을 화면에 적용하지 않는다. 결과 화면에서 작성 화면으로 돌아가 직접 수정하고 다시 검사할 수 있다. 확인 완료·오탐 판정 버튼이나 후보별 검토 상태 저장은 아직 없다.

## 5 저장과 불러오기 계약

### 5.1 사용자가 보는 동작

첫 저장은 추천 파일명을 확인·수정하고 Windows 파일 선택 창에서 위치를 고르는 순서다. 이후 저장 또는 Ctrl+S는 같은 파일을 갱신한다. 다른 이름으로 저장은 다른 파일로 이어서 작업하며 기존 파일을 보존한다. 제목을 바꾸어도 기존 파일의 이름은 자동으로 바뀌지 않는다.

파일 이름을 바꾸거나 폴더를 옮겨도 유효한 작업 파일을 직접 선택하면 다시 열 수 있다. 파일의 이름이 아닌 내부 제목을 복원한다. 마지막 저장 이후의 미저장 변경은 강제 종료·전원 차단 시 복구를 보장하지 않는다.

### 5.2 작업 파일 형식

확장자는 `.piipost`, 내용은 UTF-8 JSON이다. `format`, `version`, `title`, `body`, `savedAt`을 저장한다. 검사 결과·후보 목록·인증 토큰·모델 상태·검토 판정은 저장하지 않는다. 불러온 뒤 다시 검사한다. 파일 형식은 암호화가 아니다.

```json
{
  "format": "before-post-document",
  "version": 1,
  "title": "가상 모임 안내",
  "body": "게시할 글의 내용",
  "savedAt": "2026-10-16T00:00:00+00:00"
}
```

### 5.3 파일명과 예외 처리

`< > : " / \ | ? *`와 제어문자를 제거하고 공백·끝의 점을 정리한다. 비어 있으면 ‘제목 없음’을 제안하고, Windows 예약 이름은 조정한다. 이름 부분은 약 120 UTF-16 단위 한도로 제한하며 실제 전체 경로 제약은 OS에서 확인한다. 원제목은 변경하지 않는다. 파일명에도 개인정보가 들어갈 수 있으므로 사용자가 수정할 수 있어야 한다.

전용 창 저장은 같은 폴더의 임시 파일에 내용을 쓰고 동기화한 뒤 원래 파일을 교체한다. 실패하면 기존 정상 파일을 보존하도록 처리한다. 갑작스러운 종료 시 `.before-post-*.tmp`가 남을 수 있으며 자동 복구본으로 보장하지 않는다.

파일 해시로 외부 수정 여부를 확인하고, 파일이 바뀌었으면 다른 이름으로 저장하도록 안내한다. 손상 파일, 지원하지 않는 버전, 크기 초과, 읽기·쓰기 실패에서 현재 작성 중인 글을 유지한다. 확장자는 저장 선택 단계에서 확인하며, 선택 후 임의로 확장자를 붙여 OS 덮어쓰기 확인을 우회하지 않는다.

새 글·다른 파일 열기·정상 종료 시 미저장 변경이 있으면 저장하고 계속, 저장하지 않고 계속, 취소를 구분한다. 저장 취소나 실패를 저장 완료로 처리하지 않는다. 미저장 안내에서 시작한 저장을 취소했을 때 이전 이동 요청이 다음 저장에서 뒤늦게 실행되지 않도록 처리했다.

## 6 기술 구조와 수정 위치

### 6.1 실행 구성

실행 흐름은 `게시전 실행.vbs` → `scripts/start.ps1` → `run.py` → 로컬 FastAPI 서버와 pywebview 창이다. `run.py`는 `.runtime/python`을 읽고, `dist`의 화면을 제공한다. 기본 창은 WebView2를 사용한다. Node.js와 pnpm은 설치·화면 빌드에 필요하며 평소 검사 실행은 Python과 빌드된 화면을 사용한다.

Windows 뮤텍스로 같은 프로젝트의 일반 실행 중복을 막는다. 서버는 OS가 배정한 빈 포트를 사용한다. 전용 창을 닫으면 서버도 종료한다. 브라우저·headless 개발 모드는 해당 터미널에서 Ctrl+C로 종료한다.

확인한 환경은 Windows x64, Python 3.12.14, Node.js 24.19.0, pnpm 11.25.0이다. 주요 고정 패키지는 React/React DOM 19.3.1, TypeScript 7.0.2, Vite 8.3.4, FastAPI 0.143.2, ko-pii 1.16.0, pywebview 6.2.1이다. 전체 의존성은 잠금 파일을 기준으로 한다. 다른 조합의 호환성을 추정하지 않는다.

### 6.2 검사 데이터 흐름

React에서 제목·본문·revision을 `/api/check`로 보낸다. 서버는 입력을 검사하고 별도 spawn 프로세스에서 `detect_all`을 실행한다. 제목과 본문은 각각 검사한다. 결과의 문자 구간이 원문과 맞는지, 서로 겹치지 않는지 확인한 뒤 브라우저에 맞는 UTF-16 위치로 변환한다.

반환 후보에는 `id`, `source`, `start`, `end`, `text`, `label`, `labelName`, `risk`가 있다. 응답에는 `revision`, `engine`, `elapsedMs`도 있다. 구간은 시작 포함·끝 제외다. 엔진의 confidence와 evidence는 현재 제품 응답에서 제외되어 있다.

Python의 문자 수와 JavaScript의 UTF-16 위치는 이모지 등에서 달라진다. 기존 변환을 제거하거나 새 모델의 토큰 위치를 그대로 UI에 전달하면 마커가 잘못된 글자를 가리킬 수 있다. 새 탐지 경로도 반드시 원문에 대응하는 문자 구간을 반환해야 한다.

### 6.3 한도와 오류 처리

- 제목 300자, 본문 30,000자. 앱의 글자 수는 코드포인트 기준으로 맞춘다.
- 작업 파일 최대 2,000,000바이트, HTTP POST 본문 최대 500,000바이트.
- 서버 검사 시간 제한 20초. 진행 중 중복 검사는 busy 응답으로 처리한다.
- 시간 초과·오류 뒤 작업 프로세스를 정리하며 원문을 예외 메시지에 포함하지 않는다.
- 정적 파일 접근은 배포 폴더 안으로 제한한다. HTML처럼 보이는 사용자 입력도 텍스트로 렌더링한다.

### 6.5 API 계약

브라우저 모드에서는 `src/files.ts`가 브라우저의 파일 선택 API를 사용한다. 전용 창은 backend 파일 API를 사용한다. 두 경로의 문서 검증과 파일명 규칙이 달라지지 않도록 변경 시 함께 점검한다. `pnpm dev`만 실행하면 검사 서버와 부팅 토큰 주입까지 완성되는 구성은 아니다. 전체 기능 확인은 빌드 후 `run.py --browser` 또는 기본 전용 창으로 한다.

## 7 로컬 처리와 데이터 관리

### 7.1 같은 인터넷을 사용하는 사람에게 보이는가

현재 서버는 127.0.0.1에서만 수신하므로 같은 Wi-Fi나 LAN을 쓴다는 이유만으로 다른 기기에서 앱 서버에 접속할 수 있는 구조가 아니다. 수신 주소를 0.0.0.0이나 PC의 LAN 주소로 바꾸면 이 전제가 달라진다. 스마트폰에서 PC에 접속하는 기능은 구현하지 않았다.

Host·Origin·Sec-Fetch-Site와 세션 토큰을 확인하고, no-store 및 CSP 등의 응답 정책을 적용한다. 외부 CDN이나 AI API에 게시글을 보내지 않는다. 시험 브라우저에서는 외부 요청이 없었고 실제 프로세스의 127.0.0.1 바인딩을 확인했다. 다른 LAN 기기에서 직접 접속하는 시험과 OS 전체 통신 감시는 미실행이다.

### 7.2 보장 범위의 경계

입력 원문과 결과를 URL·앱 로그·자동 저장소에 기록하지 않는 구성이며, 직접 저장한 작업 파일에는 원문이 들어간다. 파일을 공유 폴더·동기화 폴더에 저장하거나 다른 사람에게 전달하면 앱의 로컬 서버 설정과 별개로 파일이 공유될 수 있다. OS 캐시·메모리 교환 영역이나 다른 프로그램의 접근까지 완전히 제거·차단한다고 설명하지 않는다.

현재 앱은 암호화 저장·사용자별 권한·로그인 보안을 제공하는 문서 보관함이 아니다. OneDrive 별도 정책은 보류 상태다. 최초 의존성 설치에는 인터넷이 필요하고, 준비된 현재 탐지 엔진의 검사에는 외부 서비스가 필요하지 않다. 향후 모델 추가 시에는 로컬 모델 파일·오프라인 설정과 네트워크 차단 시험을 별도로 확인해야 한다.

## 8 ko-pii 활용 범위와 위험도 해석

### 8.1 현재 사용하는 기능

설치 이름은 `ko-pii`, Python import 이름은 `ko_pii`다. 현재 제품은 1.16.0의 `detect_all`, 결과의 유형·원문 구간·위험도, 한국어 라벨 명칭을 사용한다. 기본 탐지는 정규식·사전·문맥 단서·형식 검증을 조합하며, 현재 앱에는 별도 신경망 모델이나 외부 API가 연결돼 있지 않다.

앱은 특정 소수 유형만 include로 제한하지 않고 엔진 기본 탐지 결과를 받는다. 설치된 라벨 레지스트리에는 33종이 있으나 모든 종류의 성능을 제품에서 검증한 것은 아니다. 기본 유니코드 정규화와 원문 위치 복원은 엔진에도 있다. 한글로 쓴 전화번호까지 모두 정규화된다는 뜻은 아니다.

33종은 주민·외국인·사업자·법인등록번호, 운전면허·여권·카드·토지번호, 건강보험증·처방·약품코드·팩스·계좌·사번·민원·사건번호, 전화·이메일·IP·URL·우편번호·차량·문서번호, 성명·주소·국적·학력·전공·직책, 생년월일·나이·신장·체중이다. 항목이 엔진에 있다는 사실이 해당 표현의 실제 개인정보 여부나 공개 금지 여부를 확정하지 않는다.

### 8.2 위험도와 정확도를 혼동하지 않기

현재 화면은 엔진의 CRITICAL/HIGH/MEDIUM/LOW/INFO를 심각/높음/보통/낮음/참고로 표시한다. 위험도는 우선 검토할 순서를 돕는 기준이다. 예를 들어 시험에서 이름과 전화번호는 높음, 이메일과 주소는 보통, 우편번호는 낮음, 나이와 신장·체중은 참고로 표시됐다. 모든 유형에 대한 최종 제품 정책을 별도로 확정한 것은 아니다.

‘위험도 높음’은 ‘탐지가 맞을 확률이 높음’이라는 뜻이 아니다. 차 이름 ‘박하차’를 성명으로 잘못 분류해도 성명 유형의 높음이 붙을 수 있다. confidence도 검증된 정답 확률이 아니므로 정확도 90%처럼 표현하지 않는다. 공개 행사장 주소와 개인 집 주소, 업무용과 개인 연락처의 공개 의도는 사용자가 판단한다.

### 8.3 조사했지만 아직 쓰지 않는 기능

마스킹·partial·가명화, 결합 위험도, Vault, 파일 추출, 선택적 ML 연결 등은 라이브러리 조사 대상이었다. 현재 앱의 완료 기능으로 소개하면 안 된다. 추가 기능의 실제 API와 선택한 배포판을 확인한 후 별도 구현한다. 원계획서의 ‘파일을 바로 읽는다’는 설명을 모든 파일 형식과 OCR의 자동 지원으로 해석하지 않는다.

## 9 검증 결과와 재현 가능한 오류

### 9.1 구현 검증 기록

2026년 10월 16일의 기록에서 TypeScript 검사·화면 빌드, 백엔드 자동 시험 22개, 화면 통합 시험 12개 흐름이 통과했다. 실제 Windows 창의 로딩·파일 연결·닫기 취소·서버 종료, VBS 경로의 콘솔 없는 실행과 창 표시도 확인했다.

파일 선택 창에서 경로를 고르는 동작은 자동 시험에서 임시 경로로 대체했다. 실제 파일 읽기·쓰기는 수행했고 탐지 결과는 실제 엔진을 사용했다. OS 선택창을 손으로 조작하는 최종 사용자 확인과 PC 재부팅 시험까지 끝났다는 뜻은 아니다.

초기 12개 가상 입력에서는 유형과 구간이 모두 일치한 입력이 8개였다. 이 수치는 8/12의 일반 정확도로 홍보할 자료가 아니다. 19,000자에서 가상 전화번호 후보 1,000개를 약 0.4초에 반환한 기록은 이 PC의 한 입력에 대한 관찰이다. 저사양 PC나 다른 글, 학습 모델의 성능을 보장하지 않는다.

인수인계 작성 중 재확인한 빌드와 자동 시험 결과는 자료 묶음의 `인수시점_확인기록.json`에 별도 기록한다. 이전 시험과 이번 재실행을 구분하며, 이번 문서 작성으로 제품 탐지 코드를 바꾸지는 않았다.

### 9.3 각 글에서 확인한 현상

C01에서는 ‘김하늘입니다’의 이름을 놓치고 ‘김하늘에게’의 이름은 찾았다. 한글 숫자 전화번호 `공일공-공공공공-공공공공`은 놓쳤다. `haneul [at] example [dot] com`과 표준 이메일·전화번호는 탐지했다. `서울특별시 마포구 예시로 12, 302호`의 호수는 빠졌다.

C02에서는 띄어 쓴 ‘이 가 온’과 ‘이가온입니다’의 이름을 놓쳤다. 주소의 건물명·101동·1203호가 빠졌다. 공백 전화번호와 구분자 없는 전화번호는 찾았다. 같은 더미 계좌번호도 송금 문장에서는 앞부분을 우편번호로 잡고, ‘계좌번호:’ 뒤에서는 계좌번호 전체를 찾았다. 책상 높이·무게와 ‘택배’, ‘포장재’를 잘못 표시했다.

C03은 개인정보가 없는 대조 글인데 ‘박하차’와 ‘주문번호’ 각각 두 곳을 이름으로, 선반의 180cm와 70kg을 인적 속성으로 표시했다. 이전 짧은 입력에서 오류가 났던 ‘아래’, ‘두었던’은 이 글에서는 표시하지 않았다. 단어 하나의 결과를 모든 문맥으로 일반화할 수 없다.

세 작업 파일의 실제 화면 검사에서 원문 복원, API와 후보 일치, 글자색·목록·건수, 위치 이동, 재검토 안내를 확인했고 외부 요청과 JavaScript 오류는 없었다. 화면 표시가 맞다는 검증과 탐지 판단이 맞다는 검증을 구분한다.

### 9.4 남은 사용 확인

실제 Windows 파일 선택·덮어쓰기 확인창 조작, 저장 후 PC 재부팅과 복원, 실제 전원 차단·저장장치 분리, 다른 PC 설치, 지원 Windows 버전별 동작, 다른 LAN 기기 접속 시도, OS 전체 통신 감시, 다양한 색각·보조기기 접근성, 장문·다양한 제로폭 문자와 실제 문체 평가가 남아 있다. 자동 시험 통과를 이 항목들의 통과로 바꾸어 기록하지 않는다.

## 10 논문 조사와 개선 방향

### 10.1 실제 출력에서 얻은 추가 단서

주소에서 쉼표만 제거한 비교 입력과 C01·C02 전체 글에서 동·호수까지 탐지되는 것을 확인했다. 상세 주소 기능 자체가 없기보다 구분자 처리에서 끊기는 경우가 있음을 보여준다. 사용자 원문에서 쉼표를 지워 보여주는 해결책이 아니라, 원문을 보존하며 주소 구간을 정확히 확장하는 방법을 검토한다.

올바른 김하늘과 잘못 잡힌 박하차의 confidence가 모두 0.55였고, 주문번호 오탐 중 하나는 1.0이었다. 물건의 높이·무게 오탐은 0.9였다. 전역 임계값만 높이면 일부 실제 이름을 놓치면서 높은 점수의 오탐은 남을 수 있다.

이름의 어미, 계좌 용도 문맥, 사람과 물건의 구별, 한글 숫자 연락처도 쌍으로 비교했다. 자세한 결과는 `research/detection_context_probes_v1.json`이다. 이는 원인 단서 확인이며 개선 효과를 측정한 실험이 아니다.

### 10.2 참고한 핵심 논문

**An 외 2025, De-identification of clinical notes with pseudo-labeling using regular expression rules and pre-trained BERT.** 규칙으로 만든 임시 정답을 검토해 한국어 모델을 추가 학습한 연구다. 의료 기록에서 규칙의 정밀도·재현율 97.2%·93.7%, 모델 96.5%·97.6%를 보고했다. 누락 감소와 오탐 증가의 교환을 함께 봐야 한다. 이 수치를 커뮤니티 앱의 예상 성능으로 쓰지 않는다. https://link.springer.com/article/10.1186/s12911-025-02913-z

**Chen 외 2024, Korean named entity recognition based on language-specific features.** 한국어 형태소와 개체명 경계 처리를 다룬다. 이름 뒤 조사·어미의 일관된 분리에 참고하되 형태소 분석만으로 일반 단어와 이름이 모두 구분된다고 보지 않는다. 온라인 출판은 2023년이다. https://doi.org/10.1017/S1351324923000311

**Hahm 외 2025, Thunder-DeID.** 한국어 판결문 비식별화의 자료·분류 체계·표현 확장·토큰 탐지를 다룬다. 현재 마커 UI에는 문장을 다시 생성하는 방식보다 원문 구간을 반환하는 방식이 적합하다는 설계 근거로 참고했다. 법률 문서의 숨김 기준을 커뮤니티에 그대로 적용하지 않는다. https://aclanthology.org/2025.findings-emnlp.682/

**Zaratiana 외 2024, GLiNER.** 유형 설명을 활용하는 구간 탐지 모델이다. 비교 후보가 될 수 있지만 원논문의 한국어 제로샷 결과와 트윗 문체 한계를 고려해야 한다. 표 3의 다국어 GLiNER 28.7 F1과 언어별 학습 XLM-R 55.8은 해당 논문의 설정이며 최신 모든 모델의 성능을 뜻하지 않는다. https://aclanthology.org/2024.naacl-long.300/

**Ribeiro 외 2020, Beyond Accuracy: Behavioral Testing of NLP Models with CheckList.** 전체 점수 외에 최소 기능, 의미 유지 변형, 예상 방향의 변화를 시험한다. 전화번호 구분자, 주소 쉼표, 이름 뒤 어미, 사람·물건 문맥 비교에 적용할 수 있다. https://aclanthology.org/2020.acl-main.442/

**Pilán 외 2022, The Text Anonymization Benchmark.** 반복 등장하는 개체 전체와 문서 수준의 개인정보 보호 평가를 다룬다. 같은 이름 두 곳 중 한 곳만 찾았을 때의 실패와 상세 주소 누락을 별도로 측정하는 데 참고한다. 현재 제품은 익명화 도구의 안전 보증을 제공하지 않는다. https://aclanthology.org/2022.cl-4.19/

### 10.3 권장 적용 순서

먼저 주소 구분자, 숫자 일부 매칭, 사람·물건 규격 문맥처럼 설명 가능한 오류를 보완한다. 이름과 일반 명사 구분은 한국어 NER 모델을 별도 비교 경로로 시험한다. 규칙 결과와 모델 결과를 무조건 합치지 않고 유형별로 검증된 역할을 부여한다.

정답 자료에는 놓친 정보와 개인정보가 없는 글을 함께 포함한다. ko-pii가 찾은 후보만 정답으로 검토하면 미탐이 학습 자료에서도 사라진다. 지금의 3개 글은 이미 분석했으므로 회귀 시험용으로 쓰고 최종 성능을 평가하는 독립 자료로 사용하지 않는다.

글·문장 틀 단위로 학습과 평가를 나누어 이름만 다른 같은 문장이 양쪽에 들어가지 않도록 한다. 유형별 정밀도·재현율, 전체 구간 일치, 글당 오탐 수, 반복 정보의 전체 탐지, 처리 시간과 메모리를 함께 측정한다. 초기 비교 문장 300~600개와 완성 글 100~200개는 조사에서 제안한 시작 규모이며 확정 목표나 논문의 최소 수량이 아니다.

## 11 학습 모델 연결에 대한 인수 사항

### 11.1 연결과 학습의 차이

‘모델 연결’은 학습된 탐지기를 ko-pii와 함께 검사에 사용하도록 연결하는 것이다. 기존 공개 모델을 사용할 수도 있고, 기존 한국어 모델에 커뮤니티 정답 자료를 추가 학습시킨 모델을 사용할 수도 있다. 후자가 프로젝트에 맞는 ‘우리 모델’에 가깝다. 처음부터 대규모 모델을 학습해야 한다는 의미는 아니다.

글을 자주 검사하거나 오탐 버튼을 누르는 것만으로 자동 학습되지 않는다. 정답 자료 수집, 주석, 학습, 독립 평가, 배포가 별도 필요하다. 현재 앱에 이 파이프라인은 없다. 학습 모델도 실제 개인정보 여부·공개 의도·동의를 완전히 판단하지 못하므로 직접 재검토 안내를 유지한다.

### 11.2 설치된 연결부에서 확인한 제약

`HFTokenNERAdapter`는 Hugging Face 토큰 분류 모델을 불러와 유형과 원문 구간을 반환한다. 호환되는 학습 모델 파일, torch와 transformers가 별도로 필요하다. 설치된 코드에는 해당 학습 예제의 완성 가중치가 배포되지 않는다는 안내가 있다. ko-pii만 설치하면 모든 기능이 학습된 모델이 따라온다고 설명하지 않는다. 다른 공개 NER 모델은 유형 의미·라벨·토크나이저와 라이선스를 확인해야 한다.

기본 최대 길이는 512토큰이며 잘라 읽는 설정이 있다. 30,000자 전체를 한 번 넣으면 뒤쪽이 빠질 수 있으므로 겹치는 구간으로 나누고 원문 위치를 복원해야 한다. 후보 부분만 재검사하면 이미 놓친 이름을 새로 찾을 수 없으므로 미탐 감소를 목표로 할 때는 모델도 전체 글을 검사해야 한다.

현재 앱은 검사마다 새 프로세스를 만든다. 큰 모델을 매번 읽으면 지연이 생길 수 있어 모델을 유지하는 작업 프로세스, 중단·시간 제한·종료 정책을 다시 설계하고 측정해야 한다. 실제 모델의 CPU 속도·메모리·GPU 필요 여부는 아직 측정하지 않았다.

### 11.3 병합 시 주의할 점

`merge_detections`에는 합집합·교집합·역할 분담 등의 방식이 있다. 합집합은 기존 오탐을 그대로 남길 수 있고 교집합은 누락을 늘릴 수 있다. `role_split` 기본값은 이름·주소·나이 등 10종을 모델에 넘기므로, 이름만 학습한 모델에 기본값을 쓰면 다른 유형의 규칙 탐지가 사라질 수 있다. 검증된 유형만 명시적으로 위임한다.

규칙과 모델의 confidence를 같은 확률처럼 평균 내지 않는다. 설치된 모델 어댑터는 EMAIL을 HIGH로 부여하지만 현재 기본 검사 예시의 EMAIL은 MEDIUM이다. 통합 때 위험도 의미가 의도치 않게 바뀌지 않도록 앱의 매핑 정책을 점검한다.

학습된 파일을 PC에 준비해 로컬로 추론할 수 있다. 모델 다운로드와 게시글 검사 단계를 분리하고, 로컬 경로와 오프라인 설정에서 네트워크 없이 검사되는지 시험한다. 연결·추가 학습은 아직 제안이며 완료된 기능이 아니다. 개념 참고: https://huggingface.co/docs/transformers/tasks/token_classification

## 12 다음 작업의 우선순위와 완료 기준

### 12.1 우선 재현과 기준 보존

인수자가 먼저 현재 버전을 실행하고 3개 합성 파일의 후보 7·9·6개를 재현한다. 오류가 있다는 이유로 정답 자료를 실제 출력에 맞춰 바꾸지 않는다. 소수 글의 오류를 없애기 위해 ‘박하차’ 같은 단어를 전역 제외하거나 모든 이름 후보를 숨기지 않는다.

Git 커밋이 없으므로 변경 전 파일 사본과 인수인계 manifest를 보관하고, 이후 버전 관리 방식은 사용자 작업 규칙에 맞춰 정한다. 사용자가 작성 중인 앱 창이나 초안을 시험으로 덮어쓰지 않는다. 별도 시험 실행과 합성 파일을 사용한다.

### 12.2 제안하는 후속 작업

1. 현재 오류와 대조 사례를 회귀 시험으로 확장하고 유형별 평가 기준을 정한다.
2. 주소 구분자와 숫자 용도, 물건의 규격 문맥을 작게 나누어 보완한다. 한 수정마다 기존 정탐 손실과 원문 위치를 함께 확인한다.
3. 한국어 NER 후보를 비교하되 제품 기본 결과는 검증 뒤 변경한다. 학습 데이터와 최종 평가 자료를 분리한다.
4. 사용자가 원하면 확인 완료·오탐 표시·원문 수정 이동 등의 검토 보조를 설계한다. 이 상태의 저장 여부도 별도로 정한다.
5. 실제 Windows 파일 선택·재부팅·다른 PC 사용을 확인한다. 설치형 또는 포터블 배포, 서명, 라이선스 고지, WebView2 제공 방식을 결정한다.

완료 기준은 오탐 감소뿐 아니라 중요 정보의 미탐 악화 여부, 상세 구간, 제목·본문 전체, 반복 등장, 0건과 실패의 구별, 저장 원문 보존, 기존 UI 연결과 로컬 처리 유지다. 정확도 수치 목표는 아직 정하지 않았으므로 다음 담당자가 임의로 합격률을 확정하지 않는다.

### 12.3 남은 선택 사항

대상 사용자 우선순위, 유형별 정확도 목표와 평가 자료, 모델 후보·라이선스·실행 자원, 최종 위험도 정책과 색상, 검토 상태·마스킹의 후속 범위, Windows 지원 버전과 배포 방식, OneDrive·암호화·자동 복구 필요성은 남은 결정이다. 이미 확정한 Windows 우선·React 구성·수동 저장·사용자 위치 선택을 다시 묻는 대신 해당 결정에 필요한 구체적 비교 결과를 준비한다.

## 13 실행과 시험 인수 절차

### 13.1 현재 PC에서 실행

프로젝트 폴더의 `게시전 실행.vbs`를 더블클릭한다. `runtime.local.json`의 Python 실행 경로와 그 옆 pythonw.exe, 프로젝트의 `.runtime/python`과 `dist`가 필요하다. 가상 예시 또는 제공한 합성 .piipost 파일로 검사한다. 사용자의 실제 글은 인수 시험 자료로 자동 수집하지 않는다.

실행 오류가 나면 README의 환경 준비를 확인한다. `.vbs`만 다른 곳으로 옮기면 상대 경로가 맞지 않는다. 실행 중인 동일 프로젝트가 있으면 먼저 사용자의 미저장 작업 여부를 확인해야 한다. 개발용 확인을 위해 기존 사용자 창을 강제 종료하지 않는다.

### 13.2 다른 Windows PC에서 준비

Python 3.12 계열, Node.js와 pnpm, WebView2 런타임을 준비한다. 검증된 정확한 버전은 6장과 잠금 파일을 참고한다. 압축의 `project` 폴더를 작업 위치로 사용하고, 해당 폴더에서 다음을 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/setup.ps1
```

Python과 pnpm이 명령으로 잡히지 않으면 setup.ps1의 `-Python`, `-Pnpm`에 실행 파일 경로를 전달한다. 스크립트는 Python 패키지를 프로젝트의 `.runtime/python`에 설치하고 pnpm 잠금 파일로 화면 의존성을 준비한 뒤 빌드한다. 새 PC의 Python 경로로 `runtime.local.json`을 생성한다. 최초 설치는 인터넷이 필요하다. 이 인수인계 ZIP은 오프라인 설치기나 EXE가 아니다.

### 13.3 개발과 기본 검사

다음 명령은 Python·pnpm이 PATH에 준비된 개발 환경 기준이다. 현재 Codex PC의 실행기가 PATH에 없다면 `runtime.local.json`의 경로를 사용한다.

```powershell
python run.py
python run.py --browser
python scripts/check/test_backend.py
pnpm run build
python scripts/check/check_desktop.py
```

`run.py`와 `run.py --browser`는 대체 실행 방식이므로 둘을 한 번에 같은 일반 실행으로 띄울 필요는 없다. 브라우저 모드는 최신 Edge/Chrome의 파일 선택 기능을 전제로 한다. 터미널의 개발 서버는 작업 후 Ctrl+C로 종료한다. headless 준비 파일의 URL은 실행마다 달라질 수 있다.

### 13.4 화면 통합 시험

첫 터미널에서 `python run.py --headless --ready-file tmp/app-ready.json`을 실행한 뒤 두 번째 터미널에서 `node scripts/check/check_ui.cjs`를 실행한다. Playwright가 Node에서 발견되지 않으면 `PLAYWRIGHT_MODULE` 환경변수에 설치 위치를 전달한다. 일반 화면 시험의 브라우저 경로는 `PLAYWRIGHT_CHROMIUM_EXECUTABLE`로 바꿀 수 있다.

합성 커뮤니티 시험은 `python scripts/evaluate/evaluate_community_cases.py`로 평가 자료를 만든다. 화면 확인은 `python run.py --headless --ready-file tmp/community-ready.json`을 켜고 `node scripts/check/check_community_ui.cjs`를 실행한다. 이 커뮤니티 스크립트의 Edge 실행 경로는 현재 PC 기준으로 고정돼 있으므로 다른 PC에서는 코드의 경로를 확인한다. 기존 시험 기록 보존이 필요하면 재실행 전에 사본을 보관한다.

`python scripts/evaluate/probe_detection_context.py`는 비교 문장 진단, `python scripts/evaluate/evaluate_detection.py`는 초기 소규모 탐지 평가에 사용한다. 자동 시험은 `tmp` 또는 지정한 합성 자료 경로를 사용한다. 준비 파일과 tmp 전체를 인수 자료로 무분별하게 복사하지 않는다.

### 13.5 자주 혼동할 상황

- 창이 안 보임: WebView2, dist, Python 경로를 확인한다. 이전에 수정한 pythonw 로그 설정과 실제 창의 표시 설정을 되돌리지 않는다.
- 저장 버튼이 실패함: 파일 접근 권한·공간·외부 수정·장치 연결을 구별한다. 실패를 저장 완료로 표시하지 않는다.
- 다른 PC에서 VBS 실행 실패: 현재 PC 전용 runtime.local.json이 아니라 setup으로 새 경로를 만든다.
- 모델 연결 후 긴 글 뒤쪽 미탐: 어댑터의 토큰 절단과 구간 합치기를 확인한다.
- 후보 수는 맞는데 색 위치가 어긋남: 원문 변경 여부, Python와 UTF-16 변환, 중복·겹침을 확인한다.
- 과거 HTML이 저장하는 것처럼 보임: 디자인 시안의 가상 동작과 실제 앱 파일 처리를 구분한다.

## 14 자료 목록과 인수 범위

### 14.1 제품과 기록

`README.md`는 실행과 구현 범위, `docs/verification/verification.md`는 시험과 미검증 범위, `docs/DEPENDENCIES.md`는 의존성 라이선스 메타데이터, `docs/verification/detection-evaluation.json`은 초기 12개 입력 결과다. 라이선스 메타데이터는 배포에 필요한 전체 고지 검토를 대신하지 않는다.

`research/구현전_결정사항과_ko_pii_검토.md`, `구현_착수전_기술선정과_로컬보안_검토.md`, `구현_확정사항과_검증기준.md`, `제품_방향과_보류_아이디어.md`, `저장_불러오기와_실행방식_게시글유형_조사.md`는 논의 과정의 기록이다. 앞 시점의 제안과 뒤 시점의 결정을 구분해서 읽는다.

`output/pdf/ko_pii_프로젝트_활용_안내서.pdf`는 엔진 활용 조사, `output/pdf/게시전_개인정보_자가진단_도구_종합보고서_v1.pdf`와 대응 DOCX는 구현 전 종합보고서다. `output/pdf/커뮤니티_게시글_3종_개인정보_탐지_점검보고서_v1.pdf`는 실제 탐지 점검 보고서다.

### 14.2 합성 글과 재현 자료

`output/community-review`에 C01·C02·C03 작업 파일, 사용안내, 점검기록, community-evaluation.json, ui-verification.json이 있다. `research/community_cases_v1.json`이 실행 전 기대 항목의 기준이다. `research/detection_context_probes_v1.json`은 추가 문맥 비교 결과다. 자료 묶음에는 일반 화면과 커뮤니티 화면 시험의 기존 캡처도 참고용으로 포함한다.

### 14.3 원계획서와 디자인 시안

원계획서 원본은 `<desktop>/게시전_개인정보_노출_자가진단_도구_프로젝트계획서_v2.docx`다. 인수인계 ZIP의 `reference`에 사본을 넣는다. 이 사본의 요구는 후속 사용자 결정으로 좁혀졌으므로 최신 구현 사양으로 단독 사용하지 않는다.

기존 시안은 Codex 시각화 폴더의 `privacy-review-markers.html`, `privacy-marker-directions.html`, `privacy-workspace-design.html`, `privacy-post-design.html`이다. ZIP의 `reference/design`에 보존한다. 구현은 프로젝트 `src`가 담당한다. 시안 자체에는 실제 ko-pii와 파일 저장이 연결돼 있지 않다.

### 14.4 인수인계 묶음에 포함하지 않는 것

`.git`, `.runtime`, `.venv`, `node_modules`, `dist`, `runtime.local.json`, 일반 tmp 내용과 사용자의 임의 작업 파일은 제외한다. 명시한 합성 .piipost만 포함한다. 런타임을 누락한 실수가 아니라 새 PC 환경과 개인 초안을 섞지 않기 위한 자료 범위다. 의존성 설치와 빌드 방법은 함께 제공한다.

`manifest.json`에 압축 항목별 크기와 SHA-256을 기록한다. 이것은 인수 시점의 내용 확인용이며 전자서명은 아니다. 인수 후 내용을 변경하면 해시는 달라진다.

## 15 다음 담당자의 시작 체크리스트

- 현재 최신 요구와 구현 상태를 읽고, 원계획서의 장기 기능을 당장 할 일로 오해하지 않는다.
- 앱을 별도 시험 환경에서 실행하고 작성·검사·저장·불러오기를 확인한다.
- 세 합성 글의 알려진 결과를 재현하고 원문·정답·엔진 버전을 보존한다.
- 자동 시험의 범위와 수동으로 남은 확인을 구분한다.
- 개선 전후에 오탐과 미탐, 원문 구간, 반복 등장, 처리 시간과 로컬 동작을 함께 비교한다.
- 학습 모델 연결을 원할 때 모델 종류·라벨·긴 글 처리·병합·실행 자원·라이선스를 검토한다.
- 기존 결정은 유지하고 미결정 사항에 필요한 비교안을 준비한다.

다음 담당자에게 전달할 시작 요청은 별도 `다음담당자_시작요청.txt`에 담았다. 이 문서의 권장 작업은 다음 요청을 이해하는 배경이며, 인수 문서에 적혔다는 이유로 배포·외부 전송·학습 실행이 자동 승인되는 것은 아니다.

## 16 인수 시점의 결론

기획·디자인·첫 구현·합성 글 점검·논문 조사가 연결된 상태다. 사용자가 바로 확인할 수 있는 Windows용 첫 프로그램은 있고, 탐지 품질에는 이름·상세 주소·숫자 문맥·물건 규격 관련 문제가 남아 있다. 다음 단계는 현재 구현을 버리고 다시 만드는 것이 아니라, 검증 기준을 유지하면서 오류를 재현하고 규칙과 모델의 개선 효과를 단계적으로 비교하는 것이다.

문서 작성 과정에서 기존 제품의 탐지 규칙과 화면 기능은 변경하지 않았다. 이전 보고서·논문의 성능 수치와 현재 앱의 실제 검증을 구별하고, 현재 완료 상태를 다음 담당자가 재현할 수 있도록 자료를 보존했다.
