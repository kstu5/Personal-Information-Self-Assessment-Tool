# 문서 화면에서 개인정보 가림·수정 검증

2026년 10월 25일 현재 PC의 실제 atonlee/koelectra-ko-pii-ner 모델과 인증된 앱 API, 브라우저 화면에서 가상 문서로 확인했다. 개인정보 검출 정확도 전체를 평가한 결과가 아니라 문서 위치 표시와 선택·수정·사본 확인의 연결을 검증한 기록이다.

## 적용 내용

Word·PowerPoint는 기존 LibreOffice로 페이지 화면을 만들고 PDF 글자 좌표와 원문 문단 문맥을 대응한다. 문서 위 위험도 표시와 오른쪽 검출 목록에서 같은 항목을 선택해 부분 가림·전체 가림·직접 수정을 지정한다. 원본 화면에는 변경 예정임을 알리고, 사본 생성 후에는 실제 저장 파일을 다시 변환해 보여준다. 이때 요약·목록은 사본의 재검사 결과로 바뀐다.

페이지 좌표는 표시 전용이며 기존 XML 수정 식별자를 바꾸지 않는다. 동일 문구라도 원문 문맥이 확인되지 않으면 점선으로 표시한다. 메모·발표자 노트·속성은 페이지에 억지로 연결하지 않고 텍스트·위치 목록에 유지한다. PDF·이미지에는 전체 후보 표시와 클릭 선택을 추가했고, 직접 영역 가림은 사용자가 별도로 켠다.

## 실제 모델·API 결과

| 가상 입력 | 후보 | 문맥으로 연결한 페이지 위치 | 페이지 밖 정보 | 실제 사본 검증 |
|---|---:|---:|---:|---|
| 이력서 DOCX | 14 | 14 | 0 | 부분·전체 가림과 직접 수정, 1쪽 사본 생성·재검사 |
| 행사운영 PPTX | 10 | 8 | 발표자 노트 2 | 부분·전체 가림과 직접 수정, 3쪽 사본 생성·재검사 |

두 문서에서 이름 하나를 부분 가림, 전화 하나를 전체 가림, 이메일 하나를 `공개 문의창구`로 수정했다. 다운로드한 파일의 XML을 별도로 읽어 변경 값을 확인했고 원본 SHA-256은 유지됐다. 이는 선택한 세 위치의 수정 시험이다. 선택하지 않은 정보와 부분 가림 값은 사본에도 남으므로 개인정보 전체 제거 또는 재검사 0건을 뜻하지 않는다.

사본을 다시 생성하면 새 해시의 화면으로 갱신되고 이전 사본 페이지 폴더는 삭제되며 원본 화면 캐시는 유지됨을 두 형식에서 확인했다. 페이지 응답에는 서버 파일 경로를 노출하지 않으며 잘못된 페이지 번호와 취소한 작업의 요청을 거부한다.

## 화면과 자동 시험

- 실제 이력서 화면에서 문서 표시 → 처리 선택 → 사본 생성 → 남은 후보 선택의 흐름을 확인했다. 실제 Word 사본의 이름 `김**`, 전화의 불투명 가림, 이메일 대체 문구를 화면과 저장 파일에서 확인했다.
- PDF의 전화 위치 클릭 후 전체 가림 선택이 집계에 반영됐다. 직접 수정 버튼은 비활성 상태이며 영역 가림만 지원한다는 안내를 확인했다. PDF 가림 저장 방식 자체는 기존 구현을 사용한다.
- 1280px 화면에서는 문서와 오른쪽 처리 패널을 나란히 표시하고 700px 화면에서는 아래로 배치되며 가로 넘침이 없음을 확인했다. 선택 버튼의 글자가 흐려지던 마우스 올림 상태도 대비를 보완했다.
- Python 정규 시험 **91개 통과**. 추가 시험은 반복 문구 문맥, 모호한 위치, UTF-16 위치·줄바꿈, 실제 슬라이드 순서, 페이지 API 인증·취소를 포함한다. 기존 Starlette 시험 클라이언트의 사용 중단 예정 경고 1건이 있다.
- TypeScript 검사·화면 빌드와 기존 가림 시험 5개를 통과했다. 실제 모델 연결은 [check_visual_review.py](../../test/check_visual_review.py)로 별도 확인했다.

## 부담과 제한

새 패키지 의존성은 추가하지 않았다. 최종 프런트엔드 빌드 파일 합계는 353,050바이트로 변경 전보다 13,655바이트(약 13.3KiB) 증가했다. 이 수치는 전송 압축 전 정적 파일 크기이며 전체 설치 용량이나 메모리 증가량이 아니다.

문서 화면을 열 때 별도 변환 프로세스를 실행하므로 최초 대기가 발생한다. 기존 단일 작업 대기열을 사용하고 원본/사본별 페이지를 캐시하며 파일별 비공개 변환 프로필을 재사용한다. 최대 40쪽·쪽당 2천만 픽셀, 변환 시간 제한을 둔다. 구현 전 도구 조사에서는 새 프로필의 작은 Office 문서 변환이 약 9초, 재사용 시 약 4초였고 변환 프로세스의 순간 메모리 부담도 있었다. [조사 원문](document-preview-feasibility-2026-10-25.md)의 측정은 실제 앱 전체 처리 시간이나 메모리 벤치마크가 아니다.

Word·PowerPoint의 필드·내장 개체·외부 그림 등 일부 구조는 페이지 변환을 제한한다. 변환 실패 시 텍스트로 계속 검토한다. 화면 변환 결과와 원래 프로그램의 배치는 다를 수 있고, 모든 Office 버전·복잡한 문서·대용량 성능을 검증하지 않았다. HWPX는 텍스트 검토·지원 범위의 수정 사본, HWP는 추출 본문 검토만 지원한다. PDF·이미지의 새 문구 입력은 지원하지 않는다.

핵심 코드·시험·이 보고서는 Git 관리 대상이며 상세 API 응답·실제 시험 사본·스크린샷은 `test/qa/visual-review/`에만 보관한다. GitHub 업로드는 별도 작업이다.
