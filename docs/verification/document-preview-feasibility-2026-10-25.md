# 문서 화면과 개인정보 검출 위치 연결 검토

이 문서는 구현 전 조사 기록이다. 이후 실제 앱에 적용한 결과와 현재 지원 범위는 [문서 화면 검증 기록](file-visual-review-2026-10-25.md)에 정리했다.

2026년 10월 25일 로컬 코드와 가상 문서를 확인한 결과입니다. 제품 기능 변경 없이 기존 도구의 변환 성능과 위치 연결의 한계를 조사했습니다.

## 결론

적용할 수 있습니다. PDF·이미지는 현재 화면에 검출 후보 전체의 위험도 표시와 양방향 선택을 추가하고, DOCX·PPTX는 이미 설치 과정에 포함된 LibreOffice로 읽기 전용 페이지 화면을 만드는 구성이 적합합니다. XLSX는 현재 셀 화면을 유지하면서 서식과 위치 표시를 보강하는 편이 낫습니다. 이번 XLSX 예시를 PDF로 바꾸면 5쪽으로 나뉘고 숨김 시트는 빠졌습니다.

HWP·HWPX는 같은 변환기로 처리된다고 보장할 수 없습니다. 이번 HWPX는 PDF 생성에 실패했고 HWP는 파일 생성·종료 코드만 성공했으나 본문이 깨졌습니다. 한컴 변환 엔진 연동 또는 사용자가 한글에서 만든 PDF를 별도로 검토하는 방식이 대안입니다. PDF만 별도 검사할 때는 원래 HWP/HWPX의 메모·변경 기록·속성 검토를 대체하지 않습니다.

화면 표시와 원본 수정 위치는 별개로 관리해야 합니다. 변환 페이지의 좌표를 Word XML 수정 위치나 원본 이미지 가림 좌표로 재사용하면 안 됩니다.

## 현재 구현에서 확인한 사항

| 형식 | 현재 화면 | 필요한 보강 |
|---|---|---|
| PDF·PNG·JPG·JPEG | 실제 페이지/이미지와 글자별 좌표, 직접 영역 가림 | 가림을 선택하기 전에도 전체 검출 후보를 위험도별 테두리로 표시. 클릭 시 목록과 상세 내용을 함께 선택 |
| DOCX·PPTX·HWPX | 추출한 텍스트·위치와 내장 이미지 | 원래 페이지/슬라이드에 가까운 읽기 전용 화면과 원문 위치 연결 |
| HWP | 추출 본문만 표시, 수정 저장 제한 | 별도 변환 지원 없이는 원래 페이지를 표시한다고 안내하지 않음 |
| XLSX | 시트·셀 화면, 숨김 셀 표시 | 너비·색상·테두리·병합 등 지원 가능한 서식과 숨김 상태를 함께 표시 |
| TXT·CSV·TSV | 행/셀 단위 텍스트 | 행·열 기반 강조 표시. 별도 문서 엔진 불필요 |

근거 코드는 [FileReview.tsx](../../src/FileReview.tsx), [documentTypes.ts](../../src/documentTypes.ts), [file_formats.py](../../backend/file_formats.py), [file_review.py](../../backend/file_review.py)입니다. `ImageReview`의 `selectedBoxes`는 현재 `partial`·`full` 처리를 선택한 후보 중심이며, 전체 위험도 후보 표시와 클릭 연결은 아직 없습니다. PDF 글자층·OCR에는 좌표가 있지만 Office 본문의 후보에는 페이지 좌표가 없습니다.

현재 위치 문자열의 `document · 문단 166` 같은 내부 위치 식별 표현은 사용자에게 문서의 의미를 충분히 전달하지 못합니다. 표시용 위치는 가능한 범위에서 `1쪽 · 기본 정보 표 · 성명`처럼 설명하고, 검증에 사용하는 원문 식별자는 별도로 유지하는 것이 좋습니다.

## 이 PC에서 측정한 부담

[측정 스크립트](../../test/benchmark_document_preview.py)로 기존 예시 6개에 대해 총 10회 실행했습니다. 정상적인 Office 변환은 각 2회이고 HWP/HWPX는 각 1회입니다. 원본 6개의 SHA-256이 모두 유지됐습니다. 실제 앱 화면·모델 검사 전체 시간의 벤치마크는 아닙니다.

| 문서 | 변환 결과 | 새 프로필에서 변환 | 같은 프로필로 새 프로세스 실행 | 변환 중 프로세스 트리 전용 메모리 최고값 |
|---|---|---:|---:|---:|
| 기존 이력서 DOCX | 1쪽, 확인 문구 유지 | 9.375초 | 3.763초 | 391.5 / 386.0MiB |
| 참가 추천서 DOCX | 1쪽, 확인 문구 유지 | 8.682초 | 3.739초 | 390.8 / 386.3MiB |
| 운영 브리핑 PPTX | 3쪽, 확인 문구 유지 | 9.039초 | 3.759초 | 386.8 / 381.3MiB |
| 배송 명단 XLSX | 5쪽, 보이는 확인 문구 유지 | 8.912초 | 3.660초 | 365.2 / 359.2MiB |
| 협조 공문 HWPX | PDF 생성 실패 | 8.907초 | 미측정 | 360.7MiB |
| 교육 안내 HWP | PDF는 생겼으나 본문 깨짐 | 9.122초 | 미측정 | 435.1MiB |

- 메모리는 약 25ms 간격으로 변환 프로세스와 자식 프로세스의 Windows private bytes를 합산해 측정했습니다. 최고값 사이의 짧은 순간은 놓칠 수 있습니다. RSS에는 공유 페이지의 중복 계상이 있어 전용 메모리와 구분했습니다.
- 위 숫자는 변환 중의 추가 프로세스 사용량입니다. 이미 실행 중인 앱·검사 모델·브라우저의 사용량은 포함하지 않습니다. 사용자가 체감하는 전체 메모리는 더 큽니다.
- 운영체제 파일 캐시를 비우지 않았습니다. 두 번째 열을 완전한 콜드 부팅 성능으로, 세 번째 열을 화면 캐시 재사용 시간으로 해석하면 안 됩니다. 세 번째도 문서를 다시 변환한 값입니다.
- 문서가 작고 예시 수가 적습니다. 실제 이력서·사진 포함 문서·복잡한 표·대용량 문서의 평균 성능으로 일반화할 수 없습니다. 기본 문구 확인은 배치·서식 전체 호환성 검증과 다릅니다.

현재 로컬 LibreOffice 폴더는 **1,597,617,704바이트, 약 1.60GB 또는 1.49GiB**입니다. 설치 스크립트는 이미 LibreOffice 준비 단계를 포함합니다. 따라서 이 기존 구성에서 재사용하면 같은 문서 엔진을 한 번 더 추가할 필요가 없습니다. LibreOffice를 빼는 경량 배포판을 별도로 만들 경우에는 이 크기가 다시 부담이 됩니다. 설치 파일 자체의 증가량이나 모든 PC의 설치 용량을 측정한 것은 아닙니다.

정상 Office 출력에서 PDF를 1.5배 이미지로 만드는 데 추가로 약 **0.024~0.128초**가 걸렸습니다. 이력서 1쪽 PNG는 약 **93KiB**, 페이지가 화면에서 RGBA로 풀린 픽셀 버퍼는 약 **4.3MiB**입니다. 브라우저·GPU 복사본을 포함한 실측 메모리는 아닙니다. 같은 A4 크기의 40쪽을 동시에 풀면 픽셀 버퍼만 약 172MiB이므로 한 번에 한 쪽과 인접 쪽만 유지하는 편이 좋습니다.

## 원문과 화면의 위치 대응

기존 실제 모델의 이력서 검출 결과를 현재 원본의 추출 본문과 대조한 뒤 변환 PDF에서 문구를 검색했습니다. 후보 14개 모두 같은 문구가 발견됐지만, **8개만 문구가 한 곳**이었고 **6개는 같은 값이 여러 곳**에 있었습니다. 후보의 완전 검출률을 새로 측정한 값이 아닙니다.

같은 성명·전화·이메일이 반복되므로 문구가 한 번 이상 발견됐다는 이유만으로 정확한 위치 연결을 완료했다고 볼 수 없습니다. Word의 표·문단, PPT의 슬라이드·도형 순서와 주변 문맥을 함께 사용하고, 연결 결과를 별도로 검증해야 합니다. 후보가 화면의 여러 곳에 걸리면 `위치 확인 필요`, 화면에 없는 메모·문서 속성은 `부가 정보`로 표시해야 합니다.

일치하지 않는 대상을 조용히 숨기거나 화면에 없는 후보를 없다고 판단해서는 안 됩니다. 발표자 노트·숨김 시트·문서 속성·변경 기록은 페이지 화면 밖에도 존재하므로 별도 검출 목록이 계속 필요합니다.

[시안 제작 스크립트](../../test/build_preview_probe.py)는 실제 이력서 검출 결과와 변환 화면으로 로컬 읽기 전용 HTML을 만듭니다. 위험도 색상, 화면/목록 클릭, 위험도 필터를 확인하기 위한 조사 시안이며 제품에 통합한 기능이 아닙니다. 점선은 같은 문구가 여러 곳에 있어 검증된 원문 대응이 없다는 뜻입니다. 수정·가림 저장은 제공하지 않습니다.

## 대안 비교

| 방식 | 장점 | 부담과 한계 | 권고 |
|---|---|---|---|
| 기존 페이지·셀 화면에 위험도 표시 | 이미 가진 좌표와 셀 위치 활용 | 원본 서식을 보여주지 못하는 형식이 남음. 새 엔진 없이도 UI 보강 가능하나 브라우저 실제 부하는 별도 측정 필요 | PDF·이미지·XLSX의 우선 작업 |
| 기존 LibreOffice로 DOCX/PPTX를 PDF로 변환한 뒤 페이지 표시 | 설치한 엔진 재사용. 로컬 처리 가능 | 위 측정처럼 변환 시 약 360~392MiB와 수 초 필요. Word/PPT와 다른 배치가 나올 수 있음 | 필요한 파일에만 요청 시 생성 |
| `docx-preview`로 브라우저에 DOCX 표시 | 별도 Office 변환 프로세스 없이 HTML로 표시 | DOCX 전용. HTML 기반이며 자동 페이지 나눔과 필드·변경 표시 등의 제한 존재. 라이브러리 추가 용량·브라우저 메모리는 이번에 실측하지 않음 | 정확한 쪽 배치보다 기본 내용 확인이 중요한 경량 모드 후보 |
| ONLYOFFICE Docs 같은 전체 문서 편집 서버 | 여러 Office 형식의 보기·편집 통합 | 공식 Windows 서버 최소 RAM 2GB, 권장 4GB 이상, 여유 디스크 40GB. 이것은 시스템 요구사항이며 실제 앱 추가 메모리·설치 크기 실측이 아님 | 현 로컬 도구의 미리보기만을 위해 도입하는 것은 권장하지 않음 |
| 한컴 통합문서뷰어 등 변환 엔진 | 공식 안내상 HWP/HWPX를 PDF·이미지 등으로 변환 가능 | 현재 설치되어 있지 않음. 제공 방식·라이선스·비용·용량·메모리는 공급사 확인 및 별도 실측 필요 | 한글 원본 화면 지원이 필수일 때 별도 검토 |

LibreOffice의 [공식 PDF 변환 문서](https://help.libreoffice.org/latest/en-US/text/shared/guide/pdf_params.html)와 [변환 필터 문서](https://help.libreoffice.org/latest/en-US/text/shared/guide/convertfilters.html), docx-preview의 [공식 README](https://github.com/VolodymyrBaydalka/docxjs), ONLYOFFICE의 [Windows 시스템 요구사항](https://helpcenter.onlyoffice.com/docs/installation/docs-community-sys-reqs-windows.aspx), 한컴 개발자의 [변환 지원 답변](https://forum.developer.hancom.com/t/hwp-hwpx/3017)을 참고했습니다.

## 권장 적용 순서

1. 화면 왼쪽 문서, 오른쪽 검출 목록과 처리 선택을 함께 표시합니다. PDF·이미지는 전체 후보를 위험도별로 표시하고 화면/목록 클릭을 연결합니다. 표시용 테두리와 실제 가림은 구분합니다.
2. DOCX·PPTX는 사용자가 `문서 화면 보기`를 열 때만 페이지를 만듭니다. 같은 파일 해시·검토 버전의 미리보기를 작업 중에 재사용하고 한 번에 하나만 변환합니다. 상시 변환 프로세스를 두지 않는 구성이 적합합니다.
3. Office 원문 식별자와 읽기 전용 페이지 대응 정보를 분리합니다. `previewAnchor` 같은 별도 대응 구조를 사용하며 기존 `candidate.asset`을 함부로 설정하지 않습니다. 현재 `asset`은 이미지 가림과 저장 경로를 선택하는 의미도 갖습니다.
4. XLSX는 현재 셀 화면에 지원 가능한 서식을 추가합니다. 숨김 영역과 메모를 별도 표시하고, 인쇄 미리보기를 정보 검토의 유일한 화면으로 사용하지 않습니다.
5. HWP/HWPX는 변환 도구가 확실한 경우에만 원래 페이지 보기로 안내합니다. 기본 텍스트/부가 정보 검토는 계속 제공합니다. 미리보기 썸네일 하나로 전체 문서를 검토했다고 표시하지 않습니다.
6. 저장 후에는 실제 수정 사본을 다시 렌더링합니다. Word에서 문자열 길이를 바꾸면 줄·쪽 배치가 달라질 수 있으므로 원본 화면 위에서 수정 결과를 추측해 보여주지 않습니다.

앱의 기존 인증된 자산 제공 경로·작업 취소·시간 제한·임시 파일 정리를 재사용하는 방식으로 구현할 수 있습니다. 문서 내용이 외부 뷰어 서비스에 자동 업로드되는 방식은 현재의 내 PC 처리 구성과 맞지 않습니다. 이번 조사에서는 새 의존성을 설치하거나 외부 서비스로 문서를 보내지 않았습니다.
